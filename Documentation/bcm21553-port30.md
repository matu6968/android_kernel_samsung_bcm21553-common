# BCM21553 Linux 3.0.101 port

This tree ports the Galaxy Y vendor kernel (BCM21553) to upstream Linux 3.0.101,
the last release of the 3.0 long-term series. It targets CM9/Android 4.0.4 on
GT-S5360 (`totoro`), with builds for `cooperve` and `tassve`, and a CM11
configuration variant.

It is a rebase of the earlier Linux 2.6.39.4 port, which in turn was
reconstructed from the vendor 2.6.35.7 sources. Vendor behaviour (memory map,
NAND layout, YAFFS format, Android drivers, USB/AOA) is unchanged.

## Source and branches

The upstream base is the signed tag `v3.0.101`, commit
`5dba9ddd98cbc7ad319d687887981a0ea0062c75` (tag object
`4db98884a58fff2b1c2c830a8b513bd190331f50`, signed by Greg Kroah-Hartman,
key `647F 2865 4894 E3BD 4571 99BE 38DB BDC8 6092 693E`).

`port/3.0.101-common` holds the shared code and the ICS defaults;
`port/3.0.101-ics` is identical to it. `port/3.0.101-cm-11.0` adds only the CM11
defconfig differences (Bluetooth stack and four HID drivers disabled). The
earlier `port/2.6.39.4-*` branches are kept.

The vendor commits are the 2.6.39.4 port's commits replayed onto 3.0.101, with
the conflicts resolved by hand, followed by small commits that adapt vendor code
to 3.0 APIs. Where a vendor hunk was only a backport of a fix that 3.0.101
already contains, the upstream code was taken.

## Changes needed for 3.0

* Shrinkers (`lowmemorykiller`, `ashmem`) take a `struct shrink_control`.
* The Android alarm driver's `struct alarm` and `alarm_*()` functions are renamed
  `android_alarm_*`; 3.0 has its own `alarm_init()`/`alarm_cancel()` in
  `kernel/time/alarmtimer.c`.
* The Broadcom NAND/OneNAND drivers register through `mtd_device_register()`;
  `CONFIG_MTD_PARTITIONS` and `add_mtd_partitions()` no longer exist.
* `kernel/cgroup.c` is the 3.0.101 code plus the Android attach-permission model:
  a generic CAP_SYS_ADMIN-or-same-uid check for subsystems without
  `can_attach()`/`can_attach_task()`, no uid check in `attach_task_by_pid()`. The
  vendor's removal of `synchronize_rcu()` from `cgroup_attach_task()` (a 3.1
  backport) is not carried, so moving processes between scheduler groups is
  slower than on the vendor kernel. `cpuset_can_attach()` no longer reads an
  uninitialised credential.
* `drivers/usb/Makefile` no longer builds `gadget/`; the Broadcom gadget stack in
  `gadget_brcm/` is built from `drivers/Makefile` as before.
* Android `extra_free_kbytes`/`min_free_order_shift`, the vendor `printk` hooks,
  the `mm_access()` CAP_SYS_RESOURCE override and the netpoll/RNDIS logging path
  are re-applied on the 3.0.101 versions of those files.

## OneNAND 128 byte OOB layout (important)

The flash is a 2-plane Muxed OneNAND with 4096 byte pages and 128 byte OOB.
Linux 3.0 changed the ECC/free-byte layout of non-Flex OneNAND with 128 byte OOB
(3 free bytes per 16 byte sector instead of 4, `subpage_sft` 2 instead of 0).
YAFFS2 keeps its 16 byte tags in the free OOB bytes, so with the 3.0 layout every
tag is read back shifted. The YAFFS2 mount scan then rejects all chunks, finds
blocks with nothing in use and **erases them immediately**. The scan does this
even for a read-only mount. A 3.0.101 kernel without the fix destroys `/system`
and `/data` on the first mount.

`drivers/mtd/onenand/onenand_base.c` therefore keeps the pre-3.0 layout
(`flexonenand_oob_128`, `subpage_sft = 0`) for 128 byte OOB, the format that the
2.6.x kernels wrote. Do not drop this when rebasing onto a newer 3.0.y, and do not
test flash-related changes on a device without first backing up the NAND
partitions and, preferably, making the OneNAND erase/write/markbad paths refuse
all requests for the first boot.

## Compatibility

The port keeps the vendor SDRAM base `0x81600000`, explicit decompressed kernel
address `0x81608000`, machine ID 477, the multimedia pool reservations (made from
the machine `.reserve` hook), the NAND layout and the YAFFS format. It selects
ARMv6K explicitly. Android wake locks, early suspend, Binder, ashmem, pmem,
logging, low-memory killing and network accounting remain enabled, and the
Broadcom composite USB gadget with the AOA ioctls is kept.

The ABI probe (`tools/port239/check_abi.py`) compares ARM32 structure sizes,
offsets and ioctl values for pmem, ashmem, Binder, logger, AOA and V4L2 against
the original 2.6.35.7 tree: all 59 values match.

## Build

Use the Android ARM EABI GCC 4.6 toolchain
(`android-4.4.4_r2`, prebuilts commit `d73a051b1fd1d98f5c2463354fb67898f0090bdb`)
and host GCC 11. The tool directory is still called `tools/port239`; its command
line is unchanged.

```sh
export CROSS_COMPILE=/path/to/arm-eabi-4.6/bin/arm-eabi-
HOSTCC=gcc-11 JOBS=6 tools/port239/build.sh /path/to/output totoro default
```

Boards are `totoro`, `cooperve` and `tassve`; the last argument is `default`,
`on` or `off` for AOA. The builder uses an external output directory, builds
`zImage` and modules, and checks that the release string is the one in the
top-level `Makefile` (`3.0.101`) and that every module's vermagic matches
(`3.0.101 preempt mod_unload ARMv6`). Kernel and the eight modules
(`bcmdhd`, `brcm-headsetsw`, `brcm_switch`, `brcm_test_drv`, `cifs`, `h6270enc`,
`hx170dec`, `oprofile`) must always be installed as a set.

## Validation

All eight configurations (ICS and CM11, each with totoro, totoro with AOA off,
cooperve and tassve) build without errors and pass `verify_build.py`.

On a GT-S5360 running CM9 (Android 4.0.4), the `totoro` kernel with its matching
modules boots Android to `sys.boot_completed=1` using the ramdisk of that CM9
build. Checked on that device:

* YAFFS2 mounts `/system`, `/data` and `/cache` (checkpoint restore and full
  scan) with no tag, ECC or erase errors;
* the vendor modules load, the baseband is detected and `rild` runs;
* Wi-Fi (`bcmdhd`) finds access points; Bluetooth registers `hci0` and starts
  `hciattach` and `bluetoothd`;
* early suspend and late resume run; the battery service reports status.

Not tested: touch (the test unit's panel is faulty), audio, camera, video
codecs, calls and mobile data (no SIM), USB mass storage and AOA, long-term
stability, the CM11 ROM, and the `cooperve` and `tassve` boards (build only).

## Security

Linux 3.0.101 was released in October 2013 and is the end of the 3.0 series. It
contains the stable fixes of that series up to then, and nothing newer: it has no
coverage for later vulnerabilities, and later fixes would have to be backported
separately.
