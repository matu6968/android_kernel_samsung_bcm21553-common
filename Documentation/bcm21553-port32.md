# BCM21553 Linux 3.2.102 port

This tree ports the Galaxy Y vendor kernel (BCM21553) to upstream Linux 3.2.102,
the last release of the 3.2 long-term series. It targets CM9/Android 4.0.4 on
GT-S5360 (`totoro`), with builds for `cooperve` and `tassve`, and a CM11
configuration variant.

It is a rebase of the Linux 3.0.101 port, which was a rebase of the Linux 2.6.39.4
port, which in turn was reconstructed from the vendor 2.6.35.7 sources. Vendor
behaviour (memory map, NAND layout, YAFFS format, Android drivers, USB/AOA) is
unchanged.

**Status:** the 3.2.102 kernel boots CM9 on a GT-S5360 with Wi-Fi, Bluetooth, the
modem RIL and the Broadcom USB gadget up (see "Testing" for what was and was not
exercised). Read the OneNAND section and "Installing" before flashing anything.

## Source and branches

The upstream base is the signed tag `v3.2.102`, commit
`f63b2b3204ea962e9cc34a223771ec973694f8bf` (tag object
`0973b8c3b985d296cf00bd34aeb8a2b1ec7d7482`, signed by Ben Hutchings, who
maintained 3.2.y, key `AC2B 29BD 34A6 AFDD B3F6 8F35 E7BF C8EC 9586 1109`).

`port/3.2.102-common` holds the shared code and the ICS defaults;
`port/3.2.102-ics` is identical to it. `port/3.2.102-cm-11.0` adds only the CM11
defconfig differences (Bluetooth stack and four HID drivers disabled). The
earlier `port/3.0.101-*` and `port/2.6.39.4-*` branches are kept.

The vendor commits are the 3.0.101 port's commits replayed onto 3.2.102, with the
conflicts resolved by hand, followed by small commits that adapt vendor code to
3.1/3.2 APIs. Where a vendor hunk was only a backport of a fix that 3.2.102
already contains, the upstream code was taken.

## Changes needed for 3.2

* `CONFIG_NEED_MACH_MEMORY_H` is selected for the Broadcom platforms so the vendor
  `mach/memory.h` (`PHYS_OFFSET`, `CONSISTENT_DMA_SIZE`) keeps being used. Boards
  set `.atag_offset` instead of `.boot_params`.
* `<linux/module.h>` is no longer pulled in implicitly. Without it `EXPORT_SYMBOL()`
  silently expands to nothing, so the vendor files that use module macros include
  it explicitly.
* The cpuidle driver keeps its state table in `struct cpuidle_driver`; the
  `enter()` handler returns the state index and sets `dev->last_residency`.
* MTD: partitions are registered with `mtd_device_parse_register()`, the Broadcom
  NAND driver uses `bbt_options`, and the vendor `panic_write` was dropped in favour
  of upstream `panic_nand_write`.
* YAFFS2 follows the 3.1/3.2 VFS: `->fsync(file, start, end, datasync)` writes back
  the page cache and takes `i_mutex` itself (the VFS stopped doing both in 3.1),
  link counts go through `set_nlink()`/`drop_nlink()`, attributes are checked with
  `setattr_prepare()` (3.2.102 carries the 4.9 name of `inode_change_ok()`).
* Bluetooth keeps the vendor `pkt_type` argument of `hci_conn_add()`/`hci_connect()`
  and the SCO `sockaddr` handling; `rfcomm` is upstream.
* `usb_ep_enable()` takes the descriptor from `ep->desc` since 3.1. The Broadcom
  gadget stack uses `usb_ep_enable_desc()`, and `usb_find_endpoint()` is declared
  again in `<linux/usb/composite.h>`.
* The vendor `xt_socket` export of `xt_socket_get4_sk()`/`xt_socket_get6_sk()`/
  `xt_socket_put_sk()` (used by `xt_qtaguid`) is re-applied; upstream only has it
  from 3.3. The vendor PPPoLAC/PPPoPNS drivers moved to `drivers/net/ppp/` together
  with upstream's PPP code.
* `drivers/input/misc/bma150.c` is the Broadcom accelerometer driver
  (`INPUT_BMA150_SMB380`); the new upstream Bosch driver with the same file name
  is not built. The vendor `zram`/`zsmalloc` pair (newer than 3.2's xvmalloc zram)
  is kept.
* `kernel/cgroup.c` is the 3.2.102 code plus the Android attach-permission model:
  a generic CAP_SYS_ADMIN-or-same-uid check for subsystems without
  `can_attach()`/`can_attach_task()`, no uid check in `attach_task_by_pid()`.
  `cgroup_attach_task()` still contains `synchronize_rcu()`, so moving processes
  between scheduler groups is slower than on the vendor kernel.
* Coherent DMA: since 3.1 `CONSISTENT_DMA_SIZE` from `<mach/memory.h>` is ignored, so
  `bcm21553_map_io()` calls `init_consistent_dma_size()`. Without it the area stays at
  2 MiB and the 3 MiB v3d buffers fail to allocate.
* `bcmdhd` (Broadcom Wi-Fi): `dhd_read_macaddr()` parsed the custom MAC address with
  `sscanf("%02X", &mac->octet[i])`, which stores an `unsigned int` into a byte array.
  The 3-byte overrun corrupted the caller's frame and oopsed in `dhdsdio_probe()` on
  3.2; it had only survived earlier kernels by stack-layout luck. It now parses into
  ints. The vendor `v3d` error path also called `kthread_stop()` on a NULL task.
* `ndo_set_multicast_list` is `ndo_set_rx_mode` in `bcmdhd`; `pm_qos_params.h` is
  `pm_qos.h`; `make_request_fn` (zram) returns `void`; `logbuf_lock` is a raw spinlock.
* `drivers/usb/Makefile` does not build `gadget/`; the Broadcom gadget stack in
  `gadget_brcm/` is built from `drivers/Makefile` as before.
* Android `extra_free_kbytes`/`min_free_order_shift`, the vendor `printk` hooks,
  the `mm_access()` CAP_SYS_RESOURCE override, the `fsync_enabled` switch and the
  netpoll/RNDIS logging path are re-applied on the 3.2.102 versions of those files.

## OneNAND 128 byte OOB layout (important)

The flash is a 2-plane Muxed OneNAND with 4096 byte pages and 128 byte OOB.
Linux 3.0 changed the ECC/free-byte layout of non-Flex OneNAND with 128 byte OOB
(3 free bytes per 16 byte sector instead of 4, `subpage_sft` 2 instead of 0).
YAFFS2 keeps its 16 byte tags in the free OOB bytes, so with the 3.x layout every
tag is read back shifted. The YAFFS2 mount scan then rejects all chunks, finds
blocks with nothing in use and **erases them immediately**. The scan does this
even for a read-only mount. A 3.x kernel without the fix destroys `/system`
and `/data` on the first mount.

`drivers/mtd/onenand/onenand_base.c` therefore keeps the pre-3.0 layout
(`flexonenand_oob_128`, `subpage_sft = 0`) for 128 byte OOB, the format that the
2.6.x kernels wrote. 3.2.102 adds `if (ONENAND_IS_NOP_1(this)) mtd->subpage_sft = 0;`
after the layout choice, which is redundant with this fix. Do not drop the fix when
rebasing onto a newer release, and do not test flash-related changes on a device
without first backing up the NAND partitions and, preferably, making the OneNAND
erase/write/markbad paths refuse all requests for the first boot.

## Installing

The boot image and all eight modules (`bcmdhd`, `brcm-headsetsw`, `brcm_switch`,
`brcm_test_drv`, `cifs`, `h6270enc`, `hx170dec`, `oprofile`) must come from the same
build; the module `vermagic` is `3.2.102`. The 3.0.101 modules do not load on 3.2.102
and vice versa. Install the modules from recovery (`/system/lib/modules`), then flash
`boot` with Heimdall. To go back, install the other kernel's modules from recovery and
flash its boot image. Take a read-only raw dump of the NAND partitions first
(`/dev/mtd/mtdNro`), in particular `efs`.

Debugging note: with `CONFIG_BRCM_KPANIC_UI_IND=y` the vendor `die()` handler paints a
crash image on the LCD before printing the oops, which blanks the screen and can swallow
the oops text. Switch it off for diagnostic builds.

## Testing

* Software: `tools/port239/build.sh` builds `totoro`, `totoro` with AOA off,
  `cooperve` and `tassve` for both the ICS and CM11 branches with the pinned
  arm-eabi-4.6 toolchain; `tools/port239/verify_build.py` checks each result. The ABI
  probe matches all 59 values (pass `--build` with the build directory, 3.2 generates
  the `asm/` wrapper headers there).
* Hardware (GT-S5360, CM9, 2026-10-27; item 3 added later from the user's own use):
  1. A flash-guarded diagnostic image (OneNAND erase/write/markbad refused, YAFFS2 scan
     statistics logged to a RAM window) reached Android with all three YAFFS2
     partitions restored from their checkpoints, the 15 MTD partitions parsed
     correctly and `/system` byte-identical afterwards.
  2. The same kernel without the guard, with matching modules, booted to
     `sys.boot_completed=1`: Wi-Fi associates and routes traffic, Bluetooth (`hci0`),
     baseband detection, SD card, input devices, battery and cpufreq are present, no
     oops. `/system` saw no writes or erases; `/data` shows two unfixed ECC reads
     from the known bad block 19.
  3. Used by hand afterwards on the same unit, on both the 3.0.101 and the 3.2.102 ICS
     builds (touchscreen repaired): touch, audio, camera, video and the other day-to-day
     functions worked; no regressions were reported against 3.0.101.
  4. Not exercised: USB AOA (accessory mode) on the host side, calls and mobile data
     (no SIM), the CM11 branch on a device, and a multi-day soak.

## Compatibility

The port keeps the vendor SDRAM base `0x81600000`, explicit decompressed kernel
address `0x81608000`, machine ID 477, the multimedia pool reservations (made from
the machine `.reserve` hook), the NAND layout and the YAFFS format. It selects
ARMv6K explicitly. Android wake locks, early suspend, Binder, ashmem, pmem,
logging, low-memory killing and network accounting remain enabled, and the
Broadcom composite USB gadget with the AOA ioctls is kept.

The ABI probe (`tools/port239/check_abi.py`) compares ARM32 structure sizes,
offsets and ioctl values for pmem, ashmem, Binder, logger, AOA and V4L2 against
the original 2.6.35.7 tree.
